ルールを足す・変えます。対象：$ARGUMENTS

CLAUDE.md「ゲーム仕様のルール」に沿って、**実装より先に**次の順で進める。

1. `docs/game-rules.md` の該当する節と、`docs/concept.md` のステージの説明を読む。似たルールがすでにあれば、それに合わせる
2. ルールを表の行で書く：`| 項目 | 値 | 設定のキー | 理由 |`
   - 値は **数を先頭に** 書き、単位を付ける（例：`12 m/s（約43 km/h）`、`1/60 s`）。`tests/config/rules-sync.test.ts` が先頭の数を読むため
   - 設定のキーは `` `GROUP.key` `` の形で1つ（1行に1キー）
   - 理由には、子ども（4〜8歳）にとっての意味を書く（分かりやすさ、怖くないこと、罰にしないこと）
3. 次に当たるものは、書く前に止めてオーナーに提案する
   - 隠れた補正（順位調整・確率操作・見えない補助）：入れるなら「補助」の表に書き、`ASSIST` でオン・オフ、初期値はオフ
   - 強い罰（最初に戻す、持ち物を失う、制限時間で失敗）
   - ステージ構成やスプリントの範囲の変更
4. `src/config/index.ts` に同じ値を足す（`as const`。`CONFIG` にも含める）
5. `npm test -- tests/config` で一致テストを通す
6. テストの一覧（`docs/test-plans/NORI-xx.md`）を書く。各行に「確かめる範囲」「確かめない範囲（理由）」を書く（1つの場合・1台・1方向しか試さないなら、そう書く）
7. サブエージェント `test-plan-reviewer`（初見。会話の流れを渡さない）に、ルールの節・一覧・テストのコードを突き合わせてもらう。指摘を「直す／直さない（理由）」に仕分けて直し、一覧に「- 初見レビュー：YYYY-MM-DD test-plan-reviewer、指摘 N（直した M・直さない K）」の行を書く
8. そのルールを確かめる単体テストを先に書く（`tests/core/`）。テストは設定の値を読み、数値を直書きしない。書いたら、実装をわざと壊して落ちるかを確かめる
9. 足した行・キー・一覧・初見レビューの結果を報告し、オーナーの承認をもらう。実装は、このあと別の手順で行う
