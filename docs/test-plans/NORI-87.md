# NORI-87 テストの一覧（タッチの端末で、最初のタップのあとに音が動き出す）

- もとの課題：音の仕組み（AudioContext）を動かす入口のうち、キー以外の最初の操作・Esc・タイトルから移ったときは、どのテストも確かめていない（NORI-73 の初見レビュー R6-73-4。`docs/test-plans/NORI-73.md` の「5 の確かめない範囲」の行。2026-11-17 にオーナーが NORI-87 に決めた）
- ルール：`docs/game-rules.md`「効果音と BGM」の「ブラウザは、ページを開いてから最初に触れる・キーを押すまで音を出さない」の段落（操作に当たるのは keydown（Esc を除く）・mousedown・マウス以外（タッチ・ペン）の pointerup・touchend。ページごとに数える）。R1-87-D：2026-11-20 にオーナーが、ルールの「タッチの pointerup」を「マウス以外（タッチ・ペン）の pointerup」に直すと決めた（実装 `src/render/sound.ts:113` と HTML の仕様に合わせる）。一覧 2 にペンの行を足した
- 作り：`src/render/sound.ts:92-124`。入口は 4 つの別々の登録（`keydown`（Esc で振り分け）・`mousedown`・`pointerup`（`pointerType` が mouse なら振り分けて捨てる）・`touchend`）で、どれも `unlock` を呼ぶ。最初の 1 回で全部の登録を外す。音の仕組みは `unlock` で初めて作るので、それまで `__noriSound.state()` は "none"
- 下調べ（2026-11-20、Chromium 158.0.8127.18。台本は一時フォルダで、リポジトリには入れていない）：
  - 何もない所を `page.touchscreen.tap` で 1 回タップすると、出るイベントは `pointerdown:touch → touchstart → pointerup:touch → touchend → mousedown → mouseup → click` の順（`hasTouch` だけでも `isMobile` を足しても同じ）。入口 3 つ（pointerup・touchend・mousedown）がどれも呼ばれ、最初の pointerup で登録が外れる。なので、何もない所のタップ 1 回のテストだけでは、pointerup の登録が壊れても touchend か mousedown で通ってしまい、気づけない
  - ▶（`#go`）とハンドルは pointerdown で `preventDefault` を呼ぶ（`src/input/touch.ts:65,84`）。Pointer Events の決まりで、そのあとの mousedown は出ない（R1-87-C）。タッチの画面（`any-pointer: coarse`）では ▶ は最初から見えている（`src/input/touch.ts:54`）ので、子どもの最初のタップが ▶ のことは多い。Playwright のタブレットの設定（`hasTouch`）でも `any-pointer: coarse` に当たることを確かめた
  - Playwright の `page.evaluate` は `userGesture: true` を付けて呼ぶ（`node_modules/playwright-core/lib/coreBundle.js:37344`）ので、ブラウザから見ると人の操作の扱いになる（`navigator.userActivation.hasBeenActive` が true。操作の前に作った AudioContext も "running"）。Chromium の起動の引数に自動再生の指定（autoplay）はない（同じ包みを探して 0 件。R1-87-E）。ブラウザ自身の「操作の前は音を止める」は E2E では再現できない
  - 公式の仕様：`touchscreen.tap` は「touchstart と touchend を出す」、`hasTouch` が要る（https://playwright.dev/docs/api/class-touchscreen ）。pointer・mouse のイベントを出すかは書いていない（上の下調べで確かめた）
- 作り方：E2E だけを足す（ゲームのコードは変えない）。入口ごとの登録は、合成のイベントを 1 種類だけ送り、音の仕組みができたか（"none" でなくなったか）で確かめる（一覧 2）。本物のタップ・キーの道は、一覧 1・3・4 で確かめる
- 一覧を変えるときは、この表を直して初見レビューを回し直し、オーナーの承認をもらう
- 初見レビュー：2026-11-20 test-plan-reviewer、指摘 9（1回目。直した 8・直さない 1・オーナーが決める 1（R1-87-D。直す 8 に入れて数えない）。R1-87-A〜I。仕分けは `reviews-NORI-87-2026-11-20.md`。1 ポイントなので回すのは 1 回）、ハッシュ値 cdf5583c
- 承認：2026-11-20 にオーナーが OK（初見レビューの直し 8、直さない 1（R1-87-E）の理由、刈り取りの表）、ハッシュ値 eb85c77a。あわせて R1-87-D はおすすめどおりルールを直すと決めた（一覧 2 のペンの行を足すので、このあと表が変わる）
- 承認：2026-11-20 にオーナーが OK（R1-87-D の直し：一覧 2 にペンの pointerup を足し、ルールの行の文を「マウス以外（タッチ・ペン）の pointerup」にした表）、ハッシュ値 e104b3f1
