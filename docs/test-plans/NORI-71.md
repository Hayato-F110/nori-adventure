# NORI-71 テストの一覧（ステージ3・4の見た目の E2E を、運転役で近づいて時間を止めてから測る）

- 承認：まだ（初見レビューのあとにオーナーの承認をもらう）
- もとの課題：NORI-69 の総点検の仕分けの表（`docs/test-plans/e2e-audit-2026-11-13.md` の「次に直すもの」）。2026-11-13 にオーナーが NORI-69 から分けた
- 問題：3つの E2E が、0.1 秒ごとに位置を読んでキーを押し、目標に近づいたところで測る。止まる位置が PC の速さで変わるので、測る画面も変わる（NORI-67 と同じ種類）。11/13 夜、PR #60 の CI で、ステージ3の見た目（高画質）が明るさの比 1 で落ちた（輪を外して空を2回測った形）
- 直し方：NORI-67 の `installSubApproachDriver` と同じ形。運転役（E2E 用に、ゲームの状態から入力を決める仕組み）が1刻み目から操縦し、決めた所に来た刻みで時間を止める（`window.__nori.freeze`）。早送り（`stepsPerFrame` 20）では1コマの刻みの数が決まっているので、止まる刻み・機体・カメラの位置は PC の速さによらず毎回同じになる
- 一覧を変えるときは、この表を直して初見レビューを回し直し、オーナーの承認をもらう

## 調べて分かったこと（一覧の前提）

- 飛行機は入力なしでも前へ 14 m/s（`PLANE.cruiseSpeed`）、潜水艇は 4 m/s で進む。そのため、始めの画面を確かめてから走り出す形（`waitForGo`）は使わない。待った実際の時間のぶん進んでしまい、止まる位置が変わる。見た目のテストは、1刻み目から運転役が動かす
- ステージ3のカメラは、そのコマの経過時間 `frameSeconds` で機体を追う（`src/stage3Main.ts` の `placeCamera`。`1 - exp(-followSharpness × frameSeconds)`）。早送りでは毎コマ同じだけ追い、時間を止めると `frameSeconds` が 0 になって動かない（ステージ4の `freeze` と同じ作り）
- 低画質のテストは、はじめに CPU を 20 倍遅くして画質が「低」に切り替わるのを待つ。その間も運転役は刻みの数で進むので、止まる刻みは変わらない。止まったあとも描画は続くので、画質の切り替えは止まったあとの画面にも出る

## 範囲の外（理由）

- ステージ3の「上の表示」の E2E（輪を1つくぐると数が増える）は、`waitForGo` で始めの画面を確かめてから走り出す。待った時間で位置は変わるが、確かめるのは「くぐったら数が増える」という結果だけなので、止まる位置によらない（NORI-69 で運転役に直したもの）
- FPS のテスト（`stage3.spec.ts`・`stage4.spec.ts` の「30fps 以上」）は、実際の速さが要る種類（CLAUDE.md「E2E は2種類に分ける」）。キーを押したまま測るが、値は FPS だけで、止まる位置によらない
- 明るさの比の下限（3）やたからばこの光り方の値は変えない（CLAUDE.md「数値は試行錯誤で決めない」。この課題は測り方を直すだけ）
